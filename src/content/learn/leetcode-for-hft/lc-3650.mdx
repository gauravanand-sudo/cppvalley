## Problem Statement

You are given a **directed weighted graph** with `n` nodes labeled from `0` to `n-1`. The graph is described by a list of directed edges where each edge is represented as `[u, v, w]`, meaning there's a directed edge from node `u` to node `v` with weight `w`.

Each node has a **switch** that can be used at most once. When you are at node `v`, you can:

1. Choose **one incoming edge** `u → v` (where `u` is any node with an edge to `v`)
2. Temporarily reverse it to `v → u`
3. Traverse it immediately
4. The traversal cost becomes `2 × w` (twice the original weight)

Return the **minimum cost** to travel from node `0` to node `n-1`, or `-1` if it's impossible.

### Example 1
```
Input: n = 4, edges = [[0,1,4],[0,2,1],[2,1,2],[1,3,1],[2,3,5]]
Output: 6
Explanation:
Path: 0 → 2 → 1 → 3
- 0→2 (cost 1)
- At node 2, use switch on incoming edge 1→2 (original weight 2)
  Reverse it to 2→1 with cost 2×2 = 4
- 1→3 (cost 1)
Total: 1 + 4 + 1 = 6
```

### Example 2
```
Input: n = 3, edges = [[0,1,1],[2,1,1]]
Output: -1
Explanation: Cannot reach node 2 from node 0
```

## 1️⃣ Key Insight

Why Not Other Shortest Path Algorithms?
Excellent question! Let me explain why each algorithm wouldn't work well (or at all) for this problem.

#### 1. BFS (Breadth-First Search) ❌
Why it fails:

    - BFS finds shortest path in terms of number of edges, not weighted cost
    - All edges have different weights, so the path with fewest edges ≠ cheapest path

Exception: Could use BFS if we convert to 0-1 BFS with **edge decomposition**, but impractical here.

#### 2. DFS (Depth-First Search) ❌
Why it fails:

    - DFS explores blindly without considering cost
    - Would need to explore all paths to find minimum
    - Exponential time complexity: O(branching_factor^depth)
    - Example: In a dense graph with 100 nodes, DFS could explore millions of paths unnecessarily.

#### 3. Floyd-Warshall ❌
Why it's inappropriate:

    - Time complexity: O(n³)
    - For typical constraints (n up to 10⁴ or 10⁵), O(n³) is impossible
    - Space complexity: O(n²) → 10⁸ entries for n=10⁴
    - Floyd-Warshall is for all-pairs shortest paths, we only need single-source (0 to n-1)

When to use Floyd-Warshall:

    - Small n (≤ 200)
    - Need all pairs shortest paths
    - Dense graphs

#### 4. Bellman-Ford ⚠️
    - Could work, but inefficient:
    - Time: O(n × m) vs Dijkstra's O(m log n)
    - For sparse graphs (typical), m ≈ n, so:
        - Bellman-Ford: O(n²) vs Dijkstra: O(n log n)
    - Bellman-Ford needed for negative weights, but we have strictly positive weights
    - Example comparison for n=10⁵, m=2×10⁵:
        - Bellman-Ford: 10⁵ × 2×10⁵ = 2×10¹⁰ operations
        - Dijkstra: 2×10⁵ × log₂(10⁵) ≈ 3.5×10⁶ operations


#### 5. A* Search ⚠️
    - Could work if we had a good heuristic:
    - But we don't have any admissible heuristic (like Euclidean distance in grids)
    - Without heuristic, A* degenerates to Dijkstra
    - Need domain-specific knowledge for heuristic

This is a **shortest path problem with special moves**. Crucial observations:

- All costs are **positive** (original edges have positive weights, reversed edges cost `2×w` > 0)
- No negative edges exist
- No zero-cost cycles

This immediately suggests: **Dijkstra's algorithm with graph transformation**.

## 2️⃣ Why "Switch Usable Once" Doesn't Require Extra State

This is the critical insight that simplifies the problem:

**Theorem**: With strictly positive edge weights, the shortest path is always **simple** (no repeated nodes).

**Proof**:
- Repeating a node implies going through a cycle
- Cycle cost > 0 (all edges positive)
- Removing the cycle yields a cheaper path
- Therefore, optimal paths never repeat nodes

**Consequence**:
- You will never visit the same node twice
- Thus, you will never need to use the same node's switch more than once
- No need to track switch usage in our state!

## 3️⃣ Graph Transformation (Core Idea)

For each original directed edge `u → v` with weight `w`, we can create:

1. **Normal traversal**: `u → v` with cost `w`
2. **Reversed traversal**: `v → u` with cost `2 × w` (using switch at node `u`)

Wait! Careful: The reversal happens at the **destination** node. When at node `v`, you can reverse an incoming edge `u→v` to create `v→u`. So for edge `u→v`:
- Normal: `u → v` costs `w`
- Reversed: `v → u` costs `2w` (requires being at `v` first)

Thus, we build a new graph where for each original edge `(u, v, w)`:
- Add edge `u → v` with weight `w`
- Add edge `v → u` with weight `2w`

After this transformation → **plain Dijkstra** works!

## 4️⃣ Algorithm

### Steps:
1. **Build transformed graph**:
   - For each edge `(u, v, w)` in the original graph:
     - Add `u → v` with weight `w`
     - Add `v → u` with weight `2 × w`
   
2. **Run Dijkstra's algorithm** from node `0`

3. **Return** `dist[n-1]` or `-1` if unreachable

### Complexity:
- **Time**: `O((n + m) log n)` where `m` is number of edges
- **Space**: `O(n + m)`

## 5️⃣ Correctness Proof

Let's formalize why this works:

1. **Feasibility**: Any path in the original problem corresponds to a path in our transformed graph:
   - Normal edges stay as `u→v` with cost `w`
   - When using a switch at node `v` on edge `u→v`, we traverse `v→u` with cost `2w` in our graph

2. **Optimality**: The shortest path in the transformed graph corresponds to an optimal solution:
   - Dijkstra finds the minimum cost path
   - All possible switch uses are represented by the `2w` edges
   - No optimal solution is missed

3. **Switch usage limit**: Since we never revisit nodes (positive weights guarantee simple paths), each node's switch is used at most once, satisfying the constraint.

## 6️⃣ Implementation

```cpp
#include <vector>
#include <queue>
#include <climits>
using namespace std;

class Solution {
public:
    long long minimumCost(int n, vector<vector<int>>& edges) {
        // Build adjacency list for transformed graph
        vector<vector<pair<int, long long>>> graph(n);
        
        for (const auto& e : edges) {
            int u = e[0], v = e[1];
            long long w = e[2];
            
            // Original edge: u -> v with cost w
            graph[u].emplace_back(v, w);
            
            // Reversed edge (using switch): v -> u with cost 2w
            graph[v].emplace_back(u, 2 * w);
        }
        
        // Dijkstra's algorithm
        vector<long long> dist(n, LLONG_MAX);
        dist[0] = 0;
        
        // Min-heap: (distance, node)
        priority_queue<pair<long long, int>, 
                       vector<pair<long long, int>>, 
                       greater<pair<long long, int>>> pq;
        pq.emplace(0, 0);
        
        while (!pq.empty()) {
            auto [currentDist, u] = pq.top();
            pq.pop();
            
            // Skip outdated entries
            if (currentDist != dist[u]) continue;
            
            // Early exit if we reached target
            if (u == n - 1) return currentDist;
            
            // Explore neighbors
            for (const auto& [v, w] : graph[u]) {
                long long newDist = currentDist + w;
                if (newDist < dist[v]) {
                    dist[v] = newDist;
                    pq.emplace(newDist, v);
                }
            }
        }
        
        return -1; // Target not reachable
    }
};
```

### Python Implementation:
```python
import heapq
from typing import List

class Solution:
    def minimumCost(self, n: int, edges: List[List[int]]) -> int:
        # Build graph
        graph = [[] for _ in range(n)]
        for u, v, w in edges:
            graph[u].append((v, w))          # normal edge
            graph[v].append((u, 2 * w))      # reversed edge
        
        # Dijkstra
        dist = [float('inf')] * n
        dist[0] = 0
        heap = [(0, 0)]  # (distance, node)
        
        while heap:
            current_dist, u = heapq.heappop(heap)
            
            if current_dist != dist[u]:
                continue
            
            if u == n - 1:
                return current_dist
            
            for v, w in graph[u]:
                new_dist = current_dist + w
                if new_dist < dist[v]:
                    dist[v] = new_dist
                    heapq.heappush(heap, (new_dist, v))
        
        return -1
```

## 8️⃣ Common Pitfalls & Edge Cases

1. **Large weights**: Use `long long` in C++ to avoid integer overflow
2. **No path exists**: Return `-1`
3. **Self-loops**: Handle if they exist (though problem doesn't specify)
4. **Multiple edges**: Our transformation handles them naturally
5. **Start equals target**: If `n = 1`, answer should be `0`

## 9️⃣ Why This is a "Hard" Problem

Despite the simple solution, this problem is rated Hard because:

1. **Non-obvious insight**: Recognizing that switch usage doesn't need state tracking is counterintuitive
2. **Graph transformation skill**: Knowing how to encode special moves as additional edges
3. **Proof requirement**: In an interview, you'd need to justify why Dijkstra works
4. **Positive weights assumption**: Missing this leads to overly complex solutions

## 🔟 Follow-up Questions

1. **What if switch costs were different?** (e.g., `k × w` instead of `2 × w`)
   - Same solution, just change the weight multiplier

2. **What if switches could be used multiple times?**
   - Would need to track usage state → state-space Dijkstra with `(node, switches_used_mask)`

3. **What if edges could have zero or negative weights?**
   - Dijkstra fails → need Bellman-Ford
   - Switch usage might need state tracking due to possible cycles

## Summary

- **Key insight**: Positive weights guarantee simple paths → each switch used at most once automatically
- **Solution**: Transform graph by adding reverse edges with doubled weight, then run Dijkstra
- **Time**: `O((n + m) log n)`
- **Space**: `O(n + m)`

This problem beautifully demonstrates how understanding graph properties (positive weights → simple shortest paths) can dramatically simplify seemingly complex problems.
