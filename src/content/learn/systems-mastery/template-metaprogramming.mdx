# Template Metaprogramming, SFINAE & C++20 Concepts
### From Compiler Internals to Production-Grade Generic Code — Every Layer

---

## Before We Write A Single Line — The Question That Anchors Everything

Here is a function:

```cpp
template<typename T>
T add(T a, T b) {
    return a + b;
}
```

Simple. Works for `int`, `double`, `float`. Now someone calls it with a `std::string`. It works — strings have `operator+`. Then someone calls it with a custom `NetworkPacket` type that also has `operator+` (concatenation). That also works, but `NetworkPacket` addition is extremely expensive — it does a heap allocation and a copy.

You want to constrain `add` to only work with arithmetic types. How?

The naive approach:

```cpp
template<typename T>
T add(T a, T b) {
    static_assert(std::is_arithmetic_v<T>, "T must be arithmetic");
    return a + b;
}
```

This works but gives a terrible error message and the constraint isn't part of the function's interface — it's hidden inside the body. Overload resolution doesn't see it.

The SFINAE approach: cryptic, unmaintainable, but available since C++11.

The Concepts approach: clean, readable, part of the interface, available since C++20.

By the end of this lecture you will understand every layer — what templates actually are in the compiler, what SFINAE is and why it exists, how to write it correctly, and how C++20 Concepts replace it with something that should have existed from the beginning. You'll also understand why knowing both matters — Adobe's codebase has 20 years of C++11/14 code that uses SFINAE extensively.

## Chapter 1: What Templates Actually Are — The Compiler's Perspective

Most engineers think of templates as "generic functions." That's not wrong but it misses the mechanism. Understanding the mechanism explains every template behavior that seems mysterious.

### Templates Are Not Code — They Are Code Generators

When you write:

```cpp
template<typename T>
T add(T a, T b) {
    return a + b;
}
```

The compiler does **not** generate any machine code at this point. It stores the template as a **pattern** — an AST (Abstract Syntax Tree) with a placeholder `T`. No code exists until someone instantiates the template.

```cpp
add(1, 2);        // Compiler instantiates add<int>
add(1.0, 2.0);    // Compiler instantiates add<double>
add(1, 2.0);      // Error: deduction fails (T can't be both int and double)
```

Each instantiation is a separate compilation — the compiler substitutes `T = int` into the pattern and compiles the resulting code as if you had written `int add(int a, int b)` by hand.

### The Compilation Phases — Two-Phase Lookup

Template compilation happens in two phases:

**Phase 1: Template Definition**

When the compiler sees the template definition, it checks syntax and resolves names that don't depend on `T`:

```cpp
template<typename T>
T broken(T a) {
    undeclared_function();  // Phase 1 error — doesn't depend on T
    return a + 1;           // Phase 1: OK (can't check until T is known)
}
```

`undeclared_function()` is checked immediately — it doesn't depend on T, so the compiler looks it up now and finds it doesn't exist. Error at phase 1.

`a + 1` depends on T — the compiler defers checking until phase 2.

**Phase 2: Template Instantiation**

When the template is instantiated with a specific type, the compiler substitutes T and checks everything:

```cpp
broken(std::string("hello"));  // Phase 2: std::string + 1 fails — no operator+(string, int)
```

Error at phase 2 — inside the instantiation. The error message includes the full instantiation stack, which is why template error messages are notoriously long.

### Name Lookup In Templates — Dependent vs Non-Dependent

This is a source of subtle bugs:

```cpp
template<typename T>
struct Wrapper {
    void func() {
        // Non-dependent name — looked up at phase 1
        // Must be declared before template definition
        helper();  // looks for ::helper() right now
        
        // Dependent name — looked up at phase 2
        // Looked up in the context of T
        T::static_method();  // deferred
        this->member_func(); // deferred (depends on T through inheritance)
    }
};
```

The `typename` and `template` keywords in template code exist to disambiguate dependent names:

```cpp
template<typename T>
void process(T& container) {
    // Without typename: compiler assumes T::iterator is a value, not a type
    typename T::iterator it = container.begin();
    //^^^^^^^^ required: tells compiler this is a type
    
    // Without template: compiler assumes less<> is a less-than comparison
    auto result = container.template find<int>(42);
    //                       ^^^^^^^^ required: find is a template member
}
```

The compiler doesn't know what T is at phase 1. `T::iterator` could be a static member variable (value) or a type. Without `typename`, the standard says: assume it's a value. `typename` overrides this and says: it's a type.

## Chapter 2: Template Specialization — The Foundation of TMP

Before SFINAE, understand specialization. Everything in template metaprogramming builds on it.

### Full Specialization

```cpp
// Primary template
template<typename T>
struct TypeName {
    static const char* value() { return "unknown"; }
};

// Full specialization for int
template<>
struct TypeName<int> {
    static const char* value() { return "int"; }
};

// Full specialization for double
template<>
struct TypeName<double> {
    static const char* value() { return "double"; }
};

TypeName<int>::value()     // "int"
TypeName<double>::value()  // "double"
TypeName<float>::value()   // "unknown" — uses primary
```

Full specialization: you specify every template parameter completely. The compiler picks the most specialized version that matches.

### Partial Specialization

```cpp
// Primary template
template<typename T, typename U>
struct IsSame {
    static const bool value = false;
};

// Partial specialization: when both types are the same
template<typename T>
struct IsSame<T, T> {
    static const bool value = true;
};

IsSame<int, int>::value    // true — matches partial specialization
IsSame<int, double>::value // false — matches primary
```

Partial specialization lets you specialize on patterns, not just specific types. This is the foundation of type traits.

### The Compiler's Specialization Selection Rules

When you instantiate a template, the compiler:

1. Collects all matching specializations (primary + all partials that could match)
2. Ranks them by specificity (how constrained each is)
3. Picks the most specific match
4. If two are equally specific: ambiguity error

```cpp
template<typename T>           // 1: primary — matches everything
template<typename T>           // 2: partial — matches T*
template<>                     // 3: full — matches int* exactly

MyTrait<int*> — compiler picks #3 (most specific)
MyTrait<double*> — compiler picks #2 (more specific than #1)
MyTrait<double> — compiler picks #1 (only match)
```

## Chapter 3: Type Traits — The Building Blocks

Type traits are struct templates that compute properties of types at compile time. They are the vocabulary of template metaprogramming.

### Building std::is_pointer From Scratch

```cpp
// Primary: T is not a pointer
template<typename T>
struct is_pointer {
    static constexpr bool value = false;
    using type = std::false_type;
};

// Partial specialization: T* is a pointer
template<typename T>
struct is_pointer<T*> {
    static constexpr bool value = true;
    using type = std::true_type;
};

// Partial specialization: const T* is also a pointer
template<typename T>
struct is_pointer<const T*> {
    static constexpr bool value = true;
    using type = std::true_type;
};

// Helper variable template (C++14)
template<typename T>
inline constexpr bool is_pointer_v = is_pointer<T>::value;
```

Usage:

```cpp
is_pointer_v<int>     // false
is_pointer_v<int*>    // true
is_pointer_v<int**>   // true (T=int*, T* = int**)
is_pointer_v<const int*> // true
```

### Building std::remove_reference From Scratch

Type traits can also transform types:

```cpp
// Primary: T as-is
template<typename T>
struct remove_reference {
    using type = T;
};

// Lvalue reference: remove the &
template<typename T>
struct remove_reference<T&> {
    using type = T;
};

// Rvalue reference: remove the &&
template<typename T>
struct remove_reference<T&&> {
    using type = T;
};

// Helper alias (C++14)
template<typename T>
using remove_reference_t = typename remove_reference<T>::type;
```

```cpp
remove_reference_t<int>    // int
remove_reference_t<int&>   // int
remove_reference_t<int&&>  // int
remove_reference_t<int*>   // int* (pointer, not reference)
```

### std::conditional — Compile-Time If

```cpp
template<bool Condition, typename TrueType, typename FalseType>
struct conditional {
    using type = TrueType;  // default: condition is true
};

template<typename TrueType, typename FalseType>
struct conditional<false, TrueType, FalseType> {
    using type = FalseType;  // specialization: condition is false
};

template<bool B, typename T, typename F>
using conditional_t = typename conditional<B, T, F>::type;
```

```cpp
// Choose storage type based on size
conditional_t<(sizeof(T) <= 8), T, T*>
// If T fits in 8 bytes: store T directly
// Otherwise: store T* (pointer to heap)
```

This is compile-time branching. No runtime cost. The compiler generates different code for each instantiation.

## Chapter 4: SFINAE — What It Is, Why It Exists, How It Works

### The Problem SFINAE Solves

You want to have two different implementations of a function — one for types that have a `.serialize()` method, one for types that don't. How?

You can't use `if` — the condition depends on the type, not a runtime value. You can't use specialization — you'd need to specialize for every serializable type. You need something that lets the compiler **choose between overloads based on type properties.**

SFINAE is that something.

### What SFINAE Stands For

**Substitution Failure Is Not An Error**

When the compiler tries to instantiate a function template during overload resolution, it substitutes the deduced types into the template. If that substitution **fails** (produces an invalid type or expression) — the compiler does not produce an error. It simply **removes that overload from the candidate set** and continues looking.

This is the fundamental rule. Let's see what it enables.

### The Simplest SFINAE Example — Derived From First Principles

```cpp
// We want this function to exist only when T is an integer type

template<typename T>
// std::enable_if<condition, type>::type
// If condition is true: produces type (default: void)
// If condition is false: no ::type member — substitution fails!
typename std::enable_if<std::is_integral<T>::value, T>::type
only_for_integers(T x) {
    return x * 2;
}
```

Let's trace what the compiler does for `only_for_integers(42)`:

```
1. Deduce: T = int
2. Substitute T = int into return type:
   std::enable_if<std::is_integral<int>::value, int>::type
   = std::enable_if<true, int>::type
   = int  ← valid! substitution succeeds
3. Function is a valid candidate
4. Function is called
```

For `only_for_integers(3.14)`:

```
1. Deduce: T = double
2. Substitute T = double into return type:
   std::enable_if<std::is_integral<double>::value, double>::type
   = std::enable_if<false, double>::type
   = ???  ← enable_if<false> has no ::type member!
   Substitution FAILS
3. This is SFINAE: failure is not an error
4. Compiler removes this overload from candidates
5. No other candidates → compilation error: "no matching function"
   (But the error is "no matching function", not an internal template error)
```

### How std::enable_if Is Built

```cpp
// Primary: condition is true — has ::type
template<bool Condition, typename T = void>
struct enable_if {
    using type = T;
};

// Specialization: condition is false — no ::type
template<typename T>
struct enable_if<false, T> {
    // deliberately empty — no ::type
};

// Helper
template<bool B, typename T = void>
using enable_if_t = typename enable_if<B, T>::type;
```

The absence of `::type` in the false case is what causes the substitution failure. The compiler tries to access `enable_if<false>::type`, finds it doesn't exist, and SFINAE kicks in.

### Where SFINAE Can Appear — The Exact Rules

SFINAE only works in the **immediate context of the substitution** — in the function signature (return type, parameter types, template parameters). It does not work inside the function body.

```cpp
// SFINAE in return type — works
template<typename T>
enable_if_t<is_integral_v<T>, T> func(T x);

// SFINAE in parameter type — works
template<typename T>
void func(T x, enable_if_t<is_integral_v<T>>* = nullptr);

// SFINAE in template parameter — works
template<typename T, typename = enable_if_t<is_integral_v<T>>>
void func(T x);

// NOT SFINAE — hard error inside body
template<typename T>
void func(T x) {
    typename enable_if<is_integral_v<T>, T>::type y = x;
    // If T is not integral: hard error, not SFINAE
    // The function is already selected by this point
}
```

## Chapter 5: The Four SFINAE Patterns — Every One You'll See In Production

### Pattern 1: Return Type SFINAE

```cpp
// Enable this overload when T has arithmetic operations
template<typename T>
auto square(T x) -> enable_if_t<is_arithmetic_v<T>, T> {
    return x * x;
}

// Enable this overload when T is a container (has .size())
template<typename T>
auto square(T x) -> enable_if_t
    !is_arithmetic_v<T> && 
    !is_void_v<decltype(std::declval<T>().size())>,
    T
> {
    // "square" a container means duplicate its contents
    T result;
    for (auto& elem : x) result.push_back(elem);
    for (auto& elem : x) result.push_back(elem);
    return result;
}
```

This is the classic SFINAE pattern. Readable enough for simple cases, but notice how quickly the `enable_if` expression grows. For complex conditions, this becomes unmaintainable.

### Pattern 2: Template Parameter SFINAE (Dummy Parameter)

```cpp
// Using a default template parameter as the SFINAE carrier
template
    typename T,
    typename = enable_if_t<is_integral_v<T>>
    //         ↑ unnamed, defaulted — caller never provides this
    //           Exists only to create a SFINAE failure point
>
T rotate_bits(T x, int n) {
    return (x << n) | (x >> (sizeof(T) * 8 - n));
}
```

The unnamed `typename = enable_if_t<...>` is an extra template parameter with a default. It's never specified by the caller. Its only purpose is: if the enable_if fails, the template parameter list is invalid → SFINAE → overload removed.

**The problem with this pattern:** Two overloads with different conditions but same signature look identical to the compiler:

```cpp
// ERROR: these are redefinitions, not overloads
// The unnamed parameter doesn't distinguish them for overloading purposes

template<typename T, typename = enable_if_t<is_integral_v<T>>>
void func(T x) { /* integer version */ }

template<typename T, typename = enable_if_t<!is_integral_v<T>>>
void func(T x) { /* non-integer version */ }
// Compiler error: function template redefinition
```

Fix: use a non-type template parameter instead:

```cpp
template<typename T, enable_if_t<is_integral_v<T>, int> = 0>
void func(T x) { /* integer version */ }

template<typename T, enable_if_t<!is_integral_v<T>, int> = 0>
void func(T x) { /* non-integer version */ }
// Now they have different non-type parameters — not redefinitions
```

The `= 0` is the default value. The type of the parameter (`int` after the condition succeeds) is irrelevant — it exists only for SFINAE.

### Pattern 3: Detection Idiom — Checking If A Method Exists

This is the most powerful SFINAE pattern. It lets you check if a type has a specific member function, member type, or operator — at compile time.

```cpp
// We want to check if T has a .serialize() method

// Primary: T does not have serialize() — fallback
template<typename T, typename = void>
struct has_serialize : std::false_type {};

// Partial specialization: T has serialize()
// Uses void_t to detect the method
template<typename T>
struct has_serialize
    T,
    std::void_t<decltype(std::declval<T>().serialize())>
    //  ↑ void_t: if the expression inside is valid, produces void
    //            if invalid (no serialize method), substitution fails
    //            → falls back to primary template
> : std::true_type {};

// Helper
template<typename T>
inline constexpr bool has_serialize_v = has_serialize<T>::value;
```

Let's trace the mechanism:

**For a type WITH serialize():**

```
has_serialize<MySerializable, void>

Compiler tries partial specialization:
  T = MySerializable
  Second parameter = std::void_t<decltype(std::declval<MySerializable>().serialize())>

  std::declval<MySerializable>() — creates an rvalue of MySerializable
                                   without constructing it (for unevaluated context)
  .serialize() — calls serialize on it
  decltype(...) — gets the return type of serialize()
  std::void_t<return_type> — converts any type to void

  Substitution succeeds! Second param = void
  Partial specialization matches (both params are void)
  has_serialize<MySerializable> : true_type ✓
```

**For a type WITHOUT serialize():**

```
has_serialize<int, void>

Compiler tries partial specialization:
  T = int
  Second parameter = std::void_t<decltype(std::declval<int>().serialize())>

  std::declval<int>() — ok
  .serialize() — int has no serialize()!
  decltype(...) — FAILS: invalid expression
  std::void_t<???> — substitution fails

  SFINAE: partial specialization is rejected
  Falls back to primary template: has_serialize<int> : false_type ✓
```

### Building std::void_t From Scratch

```cpp
// C++17 std::void_t — simplest possible implementation
template<typename...>
using void_t = void;
// Takes any number of types, always produces void
// If any type is invalid: substitution fails (SFINAE)
// If all types are valid: produces void
```

That's it. Three lines. All the power comes from how the compiler handles substitution failures in template arguments.

### Pattern 4: decltype SFINAE For Expressions

Check if an arbitrary expression is valid:

```cpp
// Check if T supports T + T
template<typename T>
struct is_addable {
private:
    template<typename U>
    static auto test(U*) 
        -> decltype(std::declval<U>() + std::declval<U>(), std::true_type{});
    //                                                    ↑ comma operator
    //             If the addition is valid, the comma expression
    //             produces true_type{}
    
    template<typename>
    static std::false_type test(...);  // fallback
    //                       ↑ ellipsis: lowest priority in overload resolution

public:
    using type = decltype(test<T>(nullptr));
    static constexpr bool value = type::value;
};
```

The comma operator trick: `decltype(expr1, expr2)` — if `expr1` is valid, the type is `decltype(expr2)`. If `expr1` is invalid, SFINAE removes this overload.

**A complete detection idiom example for the interview:**

```cpp
// Check multiple properties at once
template<typename T>
struct is_range_serializable : std::bool_constant
    has_serialize_v<T> &&
    std::is_default_constructible_v<T> &&
    std::is_copy_assignable_v<T>
> {};

// Use it
template<typename T>
enable_if_t<is_range_serializable<T>::value>
save_to_disk(const T& obj) {
    obj.serialize();
}

template<typename T>
enable_if_t<!is_range_serializable<T>::value>
save_to_disk(const T& obj) {
    static_assert(sizeof(T) == 0, 
        "T must have serialize(), be default constructible, and copy assignable");
}
```

## Chapter 6: Why SFINAE Is Painful — Before We Learn Concepts

Before moving to Concepts, internalize why SFINAE is genuinely terrible to work with:

### Problem 1: Error Messages Are Incomprehensible

```cpp
template<typename T, enable_if_t<is_integral_v<T>, int> = 0>
void process(T x) { /* ... */ }

process(3.14);  // Error
```

Actual error message (GCC):

```
error: no matching function for call to 'process(double)'
note: candidate: 'template<class T, typename std::enable_if
  std::is_integral<T>::value, int>::type <anonymous> > void process(T)'
note: template argument deduction/substitution failed:
note: in call to 'std::enable_if<std::is_integral<double>::value, int>::type'
      within '<anonymous>'
note:   substitution of deduced template arguments in function template
        'enable_if_t<is_integral_v<T>, int> process(T)
        [with T = double, enable_if_t<is_integral_v<T>, int> = <missing>]'
        resulted in:
```

The user sees cryptic internal template machinery instead of a clear constraint violation.

### Problem 2: SFINAE Doesn't Participate In Overload Ranking

```cpp
template<typename T, enable_if_t<is_integral_v<T>, int> = 0>
void func(T x) { /* integral version */ }

template<typename T, enable_if_t<is_floating_point_v<T>, int> = 0>
void func(T x) { /* floating point version */ }
```

These work because the conditions are mutually exclusive. But if conditions overlap, you can't express "prefer this version when both match." SFINAE just removes candidates — it doesn't rank them. You need complex mutually-exclusive conditions, which becomes combinatorially explosive.

### Problem 3: It Doesn't Scale

```cpp
// Check if T is sortable:
// - Has operator
// - Has a begin() and end() that return iterators
// - Iterator's value_type supports operator
// - Has size() method
// - size() returns an integral type

// With SFINAE: a wall of enable_if, void_t, and decltype
// that fills a screen and takes 30 minutes to understand

template<typename T, typename = void_t
    decltype(std::declval<T>() < std::declval<T>()),
    decltype(std::declval<T>().begin()),
    decltype(std::declval<T>().end()),
    enable_if_t<is_integral_v<decltype(std::declval<T>().size())>>,
    decltype(
        *std::declval<typename T::iterator>() < 
        *std::declval<typename T::iterator>()
    )
>>
void sort_container(T& container) { /* ... */ }
```

This is what real SFINAE-heavy code looks like. Unreadable. Hard to write correctly. Impossible to maintain.

## Chapter 7: C++20 Concepts — The Clean Solution

Concepts give you the same power as SFINAE with:
- Readable syntax
- Clear error messages
- Participation in overload ranking
- Reusable named constraints

### What A Concept Is

A concept is a compile-time predicate on types. It's checked like a boolean expression, but the compiler uses it to constrain templates, select overloads, and generate clear error messages.

```cpp
// Define a concept
template<typename T>
concept Integral = std::is_integral_v<T>;

// Use it
template<Integral T>
T double_it(T x) { return x * 2; }

double_it(42);    // OK
double_it(3.14);  // Error: "T does not satisfy 'Integral'"
                  // Clear, human-readable error
```

### Defining Concepts — Four Forms

**Form 1: Type trait wrapper (simplest)**

```cpp
template<typename T>
concept Arithmetic = std::is_arithmetic_v<T>;

template<typename T>
concept Pointer = std::is_pointer_v<T>;

template<typename T>
concept CopyConstructible = std::is_copy_constructible_v<T>;
```

**Form 2: requires expression — checking valid expressions**

```cpp
template<typename T>
concept Serializable = requires(T obj) {
    // Each line is a requirement
    // The expression must be valid — not evaluated, just checked
    obj.serialize();           // T must have serialize()
    { obj.size() } -> std::convertible_to<size_t>;
    //              ↑ return type must convert to size_t
    T{};                       // T must be default constructible
};
```

The `requires(T obj)` block introduces a **requires expression** — a compile-time check of whether expressions involving `T` are valid. Each line is a requirement:
- `obj.serialize()` — must be a valid expression
- `{ expr } -> concept` — expr must be valid AND its type must satisfy the concept
- `T{}` — must be a valid expression (default construction)

**Form 3: Compound requirements with nested concepts**

```cpp
template<typename T>
concept Container = requires(T c) {
    typename T::value_type;               // must have value_type member
    typename T::iterator;                 // must have iterator member
    { c.begin() } -> std::same_as<typename T::iterator>;
    { c.end() }   -> std::same_as<typename T::iterator>;
    { c.size() }  -> std::convertible_to<size_t>;
    { c.empty() } -> std::convertible_to<bool>;
};

template<typename T>
concept SortableContainer = Container<T> && requires(T c) {
    // Elements must be comparable
    requires std::totally_ordered<typename T::value_type>;
    //        ↑ nested requires: check another concept on value_type
};
```

**Form 4: Concept in terms of other concepts (composition)**

```cpp
template<typename T>
concept Number = Integral<T> || std::floating_point<T>;

template<typename T>
concept SignedNumber = Number<T> && std::is_signed_v<T>;

template<typename T>
concept SmallNumber = Number<T> && (sizeof(T) <= 4);
```

### Using Concepts — Four Syntax Forms

All four are equivalent but have different readability tradeoffs:

```cpp
// Form 1: Concept as type constraint (most readable, preferred)
template<Integral T>
T add(T a, T b) { return a + b; }

// Form 2: requires clause after template parameters
template<typename T> requires Integral<T>
T add(T a, T b) { return a + b; }

// Form 3: requires clause after function signature
template<typename T>
T add(T a, T b) requires Integral<T> { return a + b; }

// Form 4: Abbreviated function template (C++20)
auto add(Integral auto a, Integral auto b) {
    return a + b;
    // auto here means "some type satisfying Integral"
    // a and b can be different Integral types
}
```

Form 1 is the most readable for simple cases. Form 2 is better when the constraint involves multiple types or complex expressions. Form 4 is concise for simple generic functions.

## Chapter 8: Concepts vs SFINAE — The Same Thing, Done Right

Let's translate every SFINAE pattern into Concepts.

### Translation 1: enable_if → requires

```cpp
// SFINAE
template<typename T, enable_if_t<is_integral_v<T>, int> = 0>
T process(T x) { return x * 2; }

// Concepts
template<std::integral T>
T process(T x) { return x * 2; }
```

### Translation 2: Detection idiom → requires expression

```cpp
// SFINAE — detect serialize()
template<typename T, typename = void>
struct has_serialize : std::false_type {};

template<typename T>
struct has_serialize<T, void_t<decltype(std::declval<T>().serialize())>>
    : std::true_type {};

template<typename T, enable_if_t<has_serialize<T>::value, int> = 0>
void save(const T& obj) { obj.serialize(); }

// Concepts — detect serialize()
template<typename T>
concept HasSerialize = requires(T obj) {
    obj.serialize();
};

template<HasSerialize T>
void save(const T& obj) { obj.serialize(); }
```

### Translation 3: Mutually exclusive overloads

```cpp
// SFINAE — requires explicit mutual exclusion
template<typename T, enable_if_t<is_integral_v<T>, int> = 0>
void display(T x) { std::cout << x << " (int)\n"; }

template<typename T, enable_if_t<is_floating_point_v<T>, int> = 0>
void display(T x) { std::cout << x << " (float)\n"; }

// Concepts — overload resolution handles it
// Concepts participate in overload ranking — no explicit exclusion needed
template<std::integral T>
void display(T x) { std::cout << x << " (int)\n"; }

template<std::floating_point T>
void display(T x) { std::cout << x << " (float)\n"; }
```

When two concept-constrained overloads match, the compiler picks the **more constrained** one. A concept that subsumes another (implies all its requirements) is more constrained.

### Translation 4: Complex detection → Composed concepts

```cpp
// SFINAE — checking multiple properties
template<typename T, typename = void_t
    decltype(std::declval<T>().begin()),
    decltype(std::declval<T>().end()),
    decltype(std::declval<T>().size()),
    typename T::value_type
>>
void process_range(T& range) { /* ... */ }

// Concepts — clean composition
template<typename T>
concept Range = requires(T r) {
    r.begin();
    r.end();
    r.size();
    typename T::value_type;
};

template<Range T>
void process_range(T& range) { /* ... */ }
```

## Chapter 9: Concept Subsumption — How Overload Ranking Works

This is the feature SFINAE cannot replicate. When multiple constrained overloads match, concepts let the compiler rank them by specificity.

### The Subsumption Rule

Concept A **subsumes** concept B if A's requirements include all of B's requirements. In overload resolution, the more constrained overload wins.

```cpp
template<typename T>
concept Animal = requires(T a) {
    a.breathe();
    a.eat();
};

template<typename T>
concept Dog = Animal<T> && requires(T d) {
    d.bark();
    d.fetch();
};
// Dog subsumes Animal (Dog requires everything Animal requires, plus more)

// Overloads
template<Animal T>
void describe(T a) { std::cout << "some animal\n"; }

template<Dog T>
void describe(T d) { std::cout << "a dog\n"; }  // more constrained

struct Labrador {
    void breathe() {}
    void eat() {}
    void bark() {}
    void fetch() {}
};

describe(Labrador{});  // calls Dog version — it's more constrained
```

With SFINAE, you'd need: `enable_if<is_dog_v<T>>` for one overload and `enable_if<is_animal_v<T> && !is_dog_v<T>>` for the other — explicit manual exclusion. Concepts subsumption handles this automatically.

### Building A Concept Hierarchy — Real Example

```cpp
// Base: anything iterable
template<typename T>
concept Iterable = requires(T c) {
    c.begin();
    c.end();
};

// More constrained: iterable with known size
template<typename T>
concept SizedIterable = Iterable<T> && requires(T c) {
    { c.size() } -> std::convertible_to<size_t>;
};

// More constrained: random-access container
template<typename T>
concept RandomAccessContainer = SizedIterable<T> && requires(T c, size_t i) {
    { c[i] } -> std::same_as<typename T::reference>;
    c.data();  // contiguous memory
};

// Overloads — compiler picks the most constrained match
template<Iterable T>
void process(T& c) {
    // Generic: linear scan
    for (auto& elem : c) handle(elem);
}

template<SizedIterable T>
void process(T& c) {
    // Can pre-allocate because we know size
    result.reserve(c.size());
    for (auto& elem : c) handle(elem);
}

template<RandomAccessContainer T>
void process(T& c) {
    // Can use SIMD, parallel algorithms, cache-friendly access
    process_simd(c.data(), c.size());
}

std::vector<int> v{1,2,3};
process(v);  // picks RandomAccessContainer version — most constrained

std::list<int> l{1,2,3};
process(l);  // picks SizedIterable version — list is sized but not random-access

std::forward_list<int> fl{1,2,3};
process(fl);  // picks Iterable version — forward_list has no size()
```

This is the architecture of modern generic code. Define a hierarchy of concepts. Write overloads for each level. The compiler automatically picks the best implementation for each type.

## Chapter 10: if constexpr — Compile-Time Branching Inside Functions

Before Concepts, even with SFINAE you still needed separate overloads for code that differs based on type properties. C++17's `if constexpr` lets you branch inside a single function:

```cpp
template<typename T>
void serialize(const T& obj) {
    if constexpr (HasSerialize<T>) {
        // This branch compiled only when T has serialize()
        obj.serialize();
    } else if constexpr (std::is_arithmetic_v<T>) {
        // This branch compiled only for arithmetic types
        write_bytes(&obj, sizeof(T));
    } else {
        // This branch compiled when neither condition holds
        static_assert(sizeof(T) == 0,
            "T must have serialize() or be arithmetic");
    }
}
```

Key difference from regular `if`:
- Regular `if`: both branches compiled, only one runs at runtime
- `if constexpr`: only the taken branch is compiled. The other branches don't need to be valid for this type.

```cpp
template<typename T>
void process(T x) {
    if constexpr (std::is_integral_v<T>) {
        // This code is ONLY compiled when T is integral
        // rotate_bits requires integral — safe because the else branch
        // is never compiled for non-integral T
        x = rotate_bits(x, 3);  // would be compile error if compiled for double
    } else {
        x = std::round(x);      // would be compile error if compiled for int
    }
    use(x);
}
```

With regular `if`, both `rotate_bits` and `std::round` would be compiled for every T — compilation failure. With `if constexpr`, only the correct branch compiles.

### Combining Concepts and if constexpr

The clearest pattern for type-dispatched behavior:

```cpp
template<typename T>
concept Drawable = requires(T obj) {
    obj.draw();
};

template<typename T>
concept Printable = requires(T obj) {
    obj.print();
};

template<typename T>
void display(const T& obj) {
    if constexpr (Drawable<T>) {
        obj.draw();
    } else if constexpr (Printable<T>) {
        obj.print();
    } else if constexpr (std::is_arithmetic_v<T>) {
        std::cout << obj << '\n';
    } else {
        static_assert(!sizeof(T),
            "T must be Drawable, Printable, or arithmetic");
    }
}
```

Single function, multiple behaviors, zero runtime cost. The `static_assert(!sizeof(T))` is a pattern for generating errors in constexpr else branches — `sizeof(T)` is always > 0, so the assertion always fails, but only for types that reach that branch.

## Chapter 11: Putting It Together — A Production-Grade Generic Buffer

Let's build something real. A buffer class that adapts its behavior based on what the element type supports — without runtime overhead.

```cpp
// Concepts for our buffer
template<typename T>
concept Trivial = std::is_trivially_copyable_v<T>;

template<typename T>
concept HasReserve = requires(T obj, size_t n) {
    obj.reserve(n);
};

template<typename T>
concept FastCopyable = Trivial<T> && (sizeof(T) <= 64);

// A generic buffer with type-specialized operations
template<typename T>
class AdaptiveBuffer {
    T* data_ = nullptr;
    size_t size_ = 0;
    size_t capacity_ = 0;

public:
    explicit AdaptiveBuffer(size_t initial_capacity = 16) {
        reserve(initial_capacity);
    }

    void push_back(const T& val) {
        if (size_ == capacity_) grow();
        
        if constexpr (Trivial<T>) {
            // Trivial types: just memcpy — no constructor call overhead
            std::memcpy(data_ + size_, &val, sizeof(T));
        } else {
            // Non-trivial: use placement new — must call constructor
            new(data_ + size_) T(val);
        }
        size_++;
    }

    // Copy operations — specialized by capability
    AdaptiveBuffer clone() const {
        AdaptiveBuffer result;
        result.reserve(size_);
        
        if constexpr (FastCopyable<T>) {
            // Small trivially-copyable types: single memcpy
            std::memcpy(result.data_, data_, size_ * sizeof(T));
            result.size_ = size_;
        } else if constexpr (Trivial<T>) {
            // Large trivially-copyable: chunked memcpy for cache efficiency
            constexpr size_t CHUNK = 64 / sizeof(T);
            for (size_t i = 0; i < size_; i += CHUNK) {
                size_t n = std::min(CHUNK, size_ - i);
                std::memcpy(result.data_ + i, data_ + i, n * sizeof(T));
            }
            result.size_ = size_;
        } else {
            // Non-trivial: must call copy constructors
            for (size_t i = 0; i < size_; i++) {
                new(result.data_ + i) T(data_[i]);
            }
            result.size_ = size_;
        }
        return result;
    }

    // Destructor — specialized
    ~AdaptiveBuffer() {
        if constexpr (!Trivial<T>) {
            // Must call destructors for non-trivial types
            for (size_t i = 0; i < size_; i++) {
                data_[i].~T();
            }
        }
        // For trivial types: no destructor calls needed
        ::operator delete(data_);
    }

private:
    void grow() {
        size_t new_cap = capacity_ == 0 ? 16 : capacity_ * 2;
        reserve(new_cap);
    }

    void reserve(size_t new_cap) {
        if (new_cap <= capacity_) return;
        
        T* new_data = static_cast<T*>(
            ::operator new(new_cap * sizeof(T), 
                          std::align_val_t{alignof(T)})
        );
        
        if (size_ > 0) {
            if constexpr (Trivial<T>) {
                std::memcpy(new_data, data_, size_ * sizeof(T));
            } else if constexpr (std::is_nothrow_move_constructible_v<T>) {
                // Prefer move over copy when available and noexcept
                for (size_t i = 0; i < size_; i++) {
                    new(new_data + i) T(std::move(data_[i]));
                    data_[i].~T();
                }
            } else {
                // Fall back to copy
                for (size_t i = 0; i < size_; i++) {
                    new(new_data + i) T(data_[i]);
                }
                for (size_t i = 0; i < size_; i++) {
                    data_[i].~T();
                }
            }
        }
        
        ::operator delete(data_, std::align_val_t{alignof(T)});
        data_ = new_data;
        capacity_ = new_cap;
    }
};
```

This single class generates radically different machine code for:
- `AdaptiveBuffer<int>`: memcpy everywhere, no constructor/destructor calls
- `AdaptiveBuffer<std::string>`: placement new, copy constructors, destructor calls
- `AdaptiveBuffer<LargeMatrix>`: move constructors (if noexcept), chunked memcpy for clone

Zero virtual dispatch. Zero runtime type checking. The decisions are made at compile time by the compiler, guided by concepts and `if constexpr`.

## Chapter 12: What An Architect Says In The Interview

**Q: "What is SFINAE and when would you use it today?"**

> "SFINAE — Substitution Failure Is Not An Error — is the rule that when the compiler substitutes template arguments during overload resolution and that substitution produces an invalid type or expression, it doesn't produce a compilation error. Instead it silently removes that overload from the candidate set and continues. This enables conditional template enablement: you can write overloads that only exist for types satisfying certain properties.
>
> Today I reach for SFINAE only when working in pre-C++20 codebases. The canonical pattern is std::enable_if in a return type, function parameter, or template parameter, combined with type traits like std::is_integral or custom detection idioms using std::void_t and decltype. The detection idiom — a primary template that falls back to false_type and a partial specialization with void_t that succeeds when a method exists — is the most powerful SFINAE technique.
>
> In new code I prefer C++20 Concepts unconditionally. Concepts have the same power, better error messages, participate in overload ranking through subsumption, and are orders of magnitude more readable."

---

**Q: "Explain the detection idiom."**

> "The detection idiom is a SFINAE pattern for checking at compile time whether a type has a specific member, method, or supports an expression. It uses two components: std::void_t, which converts any valid type expression to void, and a partial specialization that succeeds only when a given expression is valid.
>
> The structure: a primary template inherits from false_type. A partial specialization with a second template parameter defaulted to void inherits from true_type, but uses std::void_t applied to the expression you want to check as the second parameter. If the expression is valid, void_t produces void, the partial specialization matches, and you get true_type. If the expression is invalid, substitution fails in the partial specialization — SFINAE — and you fall back to the primary, getting false_type.
>
> In C++20 this entire pattern is replaced by a requires expression: `requires(T obj) { obj.method(); }` — one line instead of a full struct. Same semantics, drastically better readability."

---

**Q: "What is concept subsumption and why does it matter?"**

> "Subsumption is the mechanism by which the compiler ranks concept-constrained overloads when multiple constraints match. Concept A subsumes concept B when every type satisfying A also satisfies B — A's requirements imply B's requirements. In overload resolution, the more constrained overload — the one whose concept subsumes the other — wins.
>
> This matters because it lets you write a hierarchy of overloads that automatically select the best implementation for a type without explicit mutual exclusion conditions. You write a Sortable concept, a RandomAccessSortable concept that extends Sortable, and implement sort for each. std::vector gets RandomAccessSortable — O(n log n) with SIMD. std::list gets Sortable — merge sort. You don't need to write `enable_if<Sortable && !RandomAccessSortable>` for the list version. The subsumption relationship handles the disambiguation automatically.
>
> SFINAE cannot do this. With enable_if you must manually make conditions mutually exclusive. With concepts and subsumption, the constraint hierarchy IS the disambiguation mechanism."

## The Insight That Connects Everything

Templates, SFINAE, and Concepts are all the same idea at different levels of abstraction:

```
Templates:   generate different code for different types
SFINAE:      control which templates exist for which types
Concepts:    express those controls clearly and correctly
```

Every C++ generic programming technique is ultimately about one thing: **moving decisions from runtime to compile time.** Instead of asking "does this object have a serialize method?" at runtime (virtual dispatch, type erasure, dynamic_cast) — ask it at compile time. The answer is baked into the generated machine code. Zero overhead.

SFINAE was the best tool we had for 9 years (C++11–C++20). It worked but it was a sharp and ugly tool. Concepts are the clean version of the same idea — same power, wielded with precision instead of pain.

The architect knows both. Because the codebase you inherit will have SFINAE. The codebase you build will use Concepts.
