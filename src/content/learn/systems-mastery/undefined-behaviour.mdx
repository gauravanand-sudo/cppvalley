# Undefined Behavior — The Dangerous Kind
### Why The Compiler Is Allowed To Break Your Program, And Does

---

## Before We Start — A Program That Should Work But Doesn't

```cpp
#include <iostream>

int main() {
    int x = INT_MAX;
    if (x + 1 > x) {
        std::cout << "x+1 is greater\n";
    } else {
        std::cout << "overflow occurred\n";
    }
}
```

What does this print?

Most engineers say: "overflow occurred — INT_MAX + 1 wraps around to INT_MIN, which is less than INT_MAX."

Actual output with `g++ -O2`:

```
x+1 is greater
```

The else branch — the "overflow occurred" path — **does not exist in the compiled binary.** The compiler deleted it. Not because it's unreachable. Because the compiler assumed it could never be reached, optimized on that assumption, and produced code that is demonstrably wrong by any human reasoning.

This is undefined behavior. Not a quirk. Not a compiler bug. Correct, standard-compliant behavior from a compiler that is smarter than you in a very specific and dangerous way.

By the end of this lecture you will understand every category of UB that matters for a systems engineer, exactly what the compiler does with each one, and how to detect and eliminate them before they destroy your production system.

## Chapter 1: What Undefined Behavior Actually Is — The Contract

### The C++ Standard's Model

The C++ standard defines three categories of behavior:

**Well-defined behavior:**
The standard specifies exactly what happens. `int x = 5; int y = x + 3;` — y is 8. Always. On every conforming implementation.

**Implementation-defined behavior:**
The standard says the behavior is defined but leaves the specifics to the implementation. `sizeof(int)` — must be at least 2 bytes, but the exact value is implementation-defined. Compilers must document it.

**Undefined behavior:**
The standard places no requirements on what happens. The program can do anything — produce correct results, crash, corrupt memory, format your hard drive, or appear to work correctly in debug builds while silently destroying data in release builds.

The formal definition from the standard:

> "Behavior for which this document imposes no requirements."

That's it. No requirements. The compiler is not required to produce a warning. Not required to crash. Not required to produce wrong results consistently. Not required to do anything in particular.

### Why UB Exists — The Performance Contract

UB is not an accident or laziness. It is a deliberate design choice that enables C++ to be faster than it would otherwise be.

Consider integer overflow. The C++ standard says signed integer overflow is undefined behavior. Why not just define it as wraparound (like unsigned integers)?

Because on some architectures, signed integer overflow traps — the hardware raises an exception. If the standard required wraparound, the compiler would need to add code to prevent the trap on those architectures. That costs cycles.

More importantly: by declaring overflow UB, the compiler can assume it never happens. This enables optimizations:

```cpp
// With overflow defined as UB:
// Compiler knows x+1 > x is always true (overflow is impossible)
// → Optimizer eliminates the false branch

// With overflow defined as wraparound:
// Compiler must handle x = INT_MAX case (wraparound is possible)
// → Optimizer cannot eliminate either branch
```

The C standard committee made a choice: define certain behaviors as UB to give compilers maximum optimization freedom. C++ inherited this choice.

**The contract:** You write programs that never invoke UB. The compiler assumes you kept your end of the bargain and optimizes aggressively on that assumption. The resulting code is fast. If you break the contract — invoke UB — the compiler's assumptions are wrong, and anything can happen.

### The Most Important Mental Model

UB is not a runtime concept. It is a compile-time permission slip.

When the compiler encounters code that could only execute if UB occurred, it is permitted to assume that code is unreachable — and remove it entirely, or transform it into something completely different.

The compiler doesn't "detect" UB and "handle" it. It assumes UB doesn't exist and optimizes accordingly. The consequences are felt at runtime when reality doesn't match the compiler's assumptions.

## Chapter 2: Signed Integer Overflow — The Optimizer's Favorite Weapon

### The Hardware Reality vs The Standard

On x86-64, signed integer arithmetic wraps around in two's complement. `INT_MAX + 1` produces `INT_MIN` at the hardware level. Always. The CPU has no concept of "undefined" — it just does the arithmetic.

The C++ standard says this is UB. The compiler knows the hardware wraps around. But because the standard says UB, the compiler is not required to emit code that produces the wraparound — it can assume the overflow never happens and optimize on that assumption.

This is the gap where disasters happen.

### What The Compiler Does With The Permission

**Example 1: Loop Optimization**

```cpp
// Counts how many times we can increment before overflow
// (trying to detect overflow — naive but common)
void process(int start) {
    for (int i = start; i >= start; i++) {
        do_work(i);
    }
}
```

Human reasoning: this loop runs until `i` overflows past INT_MAX and wraps to INT_MIN, which is less than `start`. Then it stops.

Compiler reasoning: `i` starts at `start`. `i >= start` is the condition. `i` is a signed integer. Signed overflow is UB. Therefore `i` can never overflow. Therefore `i >= start` is always true (i starts at start and only increases). Therefore this is an **infinite loop**.

With `-O2`, GCC compiles this to:

```nasm
; Infinite loop — compiler proved termination is impossible
.loop:
    call do_work
    jmp .loop
```

The loop termination check is gone. The compiler didn't get it wrong. You invoked UB, and the compiler's assumption (no overflow) produced a logically consistent but catastrophically wrong result.

**Example 2: Security Vulnerability**

```cpp
// Check if allocation size will overflow before allocating
// (pattern from real CVEs)
void* safe_alloc(int count, int element_size) {
    int total = count * element_size;
    if (total < count) {  // overflow check?
        return nullptr;   // would return null on overflow
    }
    return malloc(total);
}
```

Human intent: if `count * element_size` overflows, `total` will be smaller than `count` (due to wraparound). Return null.

Compiler reasoning: `total = count * element_size`. Signed overflow is UB. So `count * element_size` never overflows. So `total >= count * element_size >= count` (assuming element_size >= 1, which is implied by reasonable usage). So `total < count` is always false. Dead code. Remove it.

With optimization: the null check disappears. `safe_alloc(1000000, 100000)` — total overflows to a small negative number — `malloc` receives a negative size (cast to size_t: a huge number), likely returns null or crashes, and the "safe" check that should have caught it is gone.

This exact pattern appears in real CVEs. Heartbleed's root cause involved a similar optimization eliminating what looked like a safety check.

**Example 3: The Opening Example — Explained**

```cpp
int x = INT_MAX;
if (x + 1 > x) {     // UB: x+1 overflows
    std::cout << "greater\n";
} else {
    std::cout << "overflow\n";
}
```

Compiler: `x + 1 > x`. Signed overflow is UB. So `x + 1` never overflows. For any non-overflowing `x + 1`: is `x + 1 > x` always true? Yes — adding 1 to a signed integer that doesn't overflow gives a larger value. Condition is always true. Else branch is unreachable. Delete it.

Result: only the "greater" branch exists in the binary.

### How To Do It Correctly

**Option 1: Use unsigned integers for wraparound arithmetic**

Unsigned overflow is defined behavior — it wraps modulo 2^N. If you want wraparound semantics, use `unsigned int` or `uint32_t`.

```cpp
uint32_t x = UINT32_MAX;
uint32_t y = x + 1;  // y == 0, well-defined
```

**Option 2: Check before computing**

```cpp
// Safe overflow check — doesn't invoke UB
bool would_overflow_add(int a, int b) {
    if (b > 0 && a > INT_MAX - b) return true;
    if (b < 0 && a < INT_MIN - b) return true;
    return false;
}
```

**Option 3: Use compiler builtins**

```cpp
int result;
if (__builtin_add_overflow(a, b, &result)) {
    // Overflow occurred — handle it
}
// result is valid if no overflow
```

GCC and Clang provide `__builtin_add_overflow`, `__builtin_sub_overflow`, `__builtin_mul_overflow`. These generate efficient code (single instruction on x86 with flag check) and correctly detect overflow without invoking UB.

**Option 4: Use C++20 `std::midpoint` and similar**

C++20 adds several arithmetic operations that are explicitly overflow-safe. For the common case of computing a midpoint:

```cpp
// UB — overflows when a + b > INT_MAX
int mid = (a + b) / 2;

// Well-defined — never overflows
int mid = std::midpoint(a, b);
```

## Chapter 3: Strict Aliasing — The Rule Nobody Knows Until It Bites Them

### What Strict Aliasing Is

The strict aliasing rule says:

> An object may only be accessed through a pointer (or reference) of its own type, a compatible type, `char*`, `unsigned char*`, or `std::byte*`.

Accessing an object through a pointer of a different type is undefined behavior.

Most engineers have never heard of this rule. They violate it constantly in "obvious" type punning. And it works fine in debug builds. Then they turn on `-O2` and mysterious bugs appear, because the compiler used the strict aliasing rule to eliminate "impossible" memory reads.

### Why The Rule Exists — The Aliasing Problem

Consider:

```cpp
void scale(float* values, int* count, int n) {
    for (int i = 0; i < *count; i++) {
        values[i] *= 2.0f;
    }
}
```

The compiler wants to optimize this loop. It wants to read `*count` once, store it in a register, and use that register for the loop bound. But it has a problem: could `values[i]` and `count` point to the same memory? Could writing to `values[i]` change `*count`?

If they could alias, the compiler must re-read `*count` from memory on every iteration — expensive.

The strict aliasing rule says: a `float*` and an `int*` cannot alias (point to the same memory) — they're different types. Therefore: `values[i] *= 2.0f` cannot change `*count`. The compiler reads `*count` once, keeps it in a register, and loops efficiently.

If `float*` and `int*` were allowed to alias, this optimization would be impossible. Every loop over an array could be reading its own bound through a differently-typed pointer. Performance would be devastated.

The price: if you actually pass overlapping memory, you've invoked UB.

### The Classic Violation — Type Punning

Type punning means reinterpreting the bit pattern of one type as another type. The classic "obvious" approach:

```cpp
// "Convert" float to its bit representation as uint32_t
float f = 1.0f;
uint32_t bits = *(uint32_t*)(&f);  // UNDEFINED BEHAVIOR
```

This violates strict aliasing: accessing a `float` object through a `uint32_t*`. The compiler is allowed to assume these don't alias — your cast doesn't change that. The compiler may:

- Read `bits` before the `float` value is written to memory (it's still in a floating-point register)
- Eliminate the load entirely (the `float` and `uint32_t` don't alias, so the `uint32_t` read is reading uninitialized memory from the compiler's perspective)
- Produce correct results in debug builds (the compiler happens to spill the float to memory) and wrong results in release builds (float stays in register, integer read gets garbage)

**Real-world manifestation:** The Fast Inverse Square Root (Quake III's famous hack):

```cpp
float Q_rsqrt(float number) {
    long i;
    float x2, y;
    const float threehalfs = 1.5F;

    x2 = number * 0.5F;
    y  = number;
    i  = *(long*)(&y);           // UB: strict aliasing violation
    i  = 0x5f3759df - (i >> 1);
    y  = *(float*)(&i);          // UB: strict aliasing violation
    y  = y * (threehalfs - (x2 * y * y));

    return y;
}
```

This "works" in practice on specific compilers with specific settings. It invokes UB twice. Under aggressive optimization it can silently produce wrong results. Modern codebases should not use this.

### The Correct Ways To Type Pun

**Option 1: memcpy — always correct, usually optimized away**

```cpp
float f = 1.0f;
uint32_t bits;
std::memcpy(&bits, &f, sizeof(bits));
// Well-defined: memcpy accesses through char*, which is allowed to alias anything
// Modern compilers optimize this to a register move — zero overhead
```

This is the standard-blessed solution. Every major compiler optimizes `memcpy` of scalar-sized values to a single instruction or register operation. The memcpy is not actually called at runtime.

**Option 2: std::bit_cast (C++20) — the clean solution**

```cpp
float f = 1.0f;
uint32_t bits = std::bit_cast<uint32_t>(f);
// Well-defined, zero overhead, expressive
// Requires: sizeof(uint32_t) == sizeof(float)
// and uint32_t is trivially copyable
```

`std::bit_cast` is explicitly defined by the standard to reinterpret the bit pattern. No UB. Compiles to a single instruction.

**Option 3: union (C, but NOT C++)**

```c
// C: this is allowed
union FloatBits {
    float f;
    uint32_t bits;
};
union FloatBits fb;
fb.f = 1.0f;
uint32_t b = fb.bits;  // OK in C99
```

In C++, reading from a union member that wasn't the last written member is UB. Do not use union type punning in C++.

**Option 4: char* and std::byte* — the escape hatch**

The strict aliasing rule explicitly exempts `char*`, `unsigned char*`, and `std::byte*`. These types are allowed to alias anything:

```cpp
float f = 1.0f;
unsigned char bytes[sizeof(float)];
std::memcpy(bytes, &f, sizeof(float));
// Reading float through unsigned char* — always legal
// Used for serialization, hashing
```

### The -fno-strict-aliasing Flag

GCC and Clang both support `-fno-strict-aliasing`, which disables strict aliasing optimizations. The Linux kernel compiles with this flag because the kernel does a lot of intentional type punning.

For user-space C++: do not use this flag as a crutch. It reduces optimization opportunities across your entire codebase. Fix the aliasing violations instead.

## Chapter 4: Data Races — UB That Destroys Everything

We covered data races in the memory model lecture. Now let's understand them specifically as UB and what the compiler does with that permission.

### A Data Race Is Not Just A Race Condition

These are different things:

**Race condition:** A logical bug where the outcome depends on timing. May or may not involve UB.

**Data race:** Two threads access the same memory location, at least one writes, with no synchronization. This is UB by definition in the C++ memory model.

A data race is not "might produce wrong results." It is undefined behavior — the compiler can transform your program in ways that produce impossible-seeming results.

### What The Compiler Does With Data Race Permission

**The hoisting optimization:**

```cpp
bool done = false;  // non-atomic, shared

// Thread 1
while (!done) {
    process_pending_work();
}

// Thread 2
// ... eventually sets done = true
```

Compiler analysis of Thread 1's loop:
- `done` is a regular (non-atomic) variable
- No writes to `done` in Thread 1's code
- Assumes no data races (no UB)
- Therefore: `done` cannot change during Thread 1's execution
- `while (!done)` either loops forever (if done starts false) or doesn't loop at all (if done starts true)
- Optimize: read `done` once before the loop

```cpp
// What the compiler generates (conceptually)
bool done_cached = done;  // read once
if (!done_cached) {
    while (true) {  // infinite loop — done can never change
        process_pending_work();
    }
}
```

Thread 2's write to `done` is a data race. The compiler's optimization is legal. Thread 1 never terminates.

**The elimination optimization:**

```cpp
int counter = 0;  // shared, non-atomic

// Thread 1
for (int i = 0; i < 1000000; i++) {
    counter++;
}

// Thread 2
for (int i = 0; i < 1000000; i++) {
    counter++;
}
```

Compiler sees Thread 1's loop. `counter++` is `counter = counter + 1`. No atomic operations. No synchronization. Assumes no data race. Therefore Thread 2 doesn't exist from Thread 1's perspective (no UB assumption). Therefore Thread 1's loop on `counter` is a simple local increment. Optimize: keep `counter` in a register for the entire loop, write once at the end.

```nasm
; Thread 1 compiled code (conceptually)
MOV eax, [counter]    ; read counter once
ADD eax, 1000000      ; add million in one instruction
MOV [counter], eax    ; write once
```

Thread 2 does the same. Final counter: 1000000, not 2000000. Not because of a race condition — because the compiler's optimization eliminated the per-iteration memory access entirely.

### The Time-Travel Effect

This is the most disturbing manifestation of data race UB. The compiler can move code across the data race point, causing operations that appear to happen before the race to be affected by it.

```cpp
int result = 0;

void thread1() {
    result = compute();          // (A) write result
    flag.store(true, relaxed);   // (B) signal thread 2
}

void thread2() {
    while (!flag.load(relaxed)); // (C) wait for signal
    use(result);                 // (D) use result
}
```

`result` is a data race (non-atomic, accessed by both threads). The compiler sees the data race and invokes UB. It is now free to reorder (A) and (B) — even move (A) after (D) from the hardware's perspective. Thread 2 can read `result` before Thread 1 has written it.

This is why you need `std::atomic` and proper memory ordering — not just to prevent bad hardware behavior, but to prevent the compiler from performing transformations that assume no concurrent access.

### What Makes This UB (Not Just A Bug)

The C++ memory model says:

> If a program contains a data race, the behavior of the entire program is undefined.

Not just the racing access. The entire program. Every piece of code in the program becomes potentially invalid once UB is introduced. The compiler can "time travel" — optimize code that appears before the race based on assumptions that only hold after it.

This is why data races in large codebases are so dangerous. The UB might manifest as corruption in a completely unrelated part of the program — data that appeared to be written correctly gets corrupted because the compiler reordered operations across an invisible race.

## Chapter 5: Unsequenced Modifications — The Evaluation Order Trap

### The Rule

Within a single expression, the order of evaluation of subexpressions is — in many cases — **unspecified**. If you modify a variable and also read or modify it elsewhere in the same expression, without a sequencing point between them, the behavior is undefined.

### The Classic Example

```cpp
int i = 0;
int arr[10] = {};
arr[i] = i++;  // UB
```

Human intent: set arr[0] to 0, then increment i.

The C++ standard says: in `arr[i] = i++`, the order of evaluation of `arr[i]` (which reads i) and `i++` (which modifies i) is unspecified. If the read and the modification are not sequenced, it's UB.

The compiler might evaluate left-to-right (arr[0] = 0, then i becomes 1) or right-to-left (i becomes 1, then arr[1] = 0) or something else entirely. With optimization, the result may be inconsistent across runs.

### Another Classic

```cpp
int i = 5;
int result = i++ + i++;  // UB
```

Most people expect 5 + 6 = 11 or 6 + 5 = 11. In practice:
- GCC -O0: 11 (left-to-right)
- GCC -O2: 10 (some architectures; compiler uses pre-increment value twice)
- Clang -O2: may differ

The actual behavior is undefined. There is no correct answer.

### The Sequencing Rules — What Is Safe

C++17 made evaluation order more specified in some cases. The key rules:

**Function arguments:** Evaluation order is unspecified (but each argument is fully evaluated before the function call).

```cpp
int i = 0;
func(i++, i++);  // UB in C++14 and earlier
                 // Still UB in C++17 (order unspecified)
```

**Assignment operator:** In C++17, the right side is sequenced before the left side for simple assignment. Not for compound assignment.

```cpp
int i = 0;
i = i + 1;    // OK in C++17: right side evaluated first
i += i++;     // Still UB: compound assignment doesn't sequence the same way
```

**Chained function calls:** In C++17, for postfix expressions, left-to-right is guaranteed.

```cpp
obj.f().g().h();  // C++17: f() sequenced before g() before h()
```

**The safe rule:** Never modify a variable and read or modify it again in the same expression unless there is an explicit sequence point (`;`, `&&`, `||`, `,` operator, `?:`) between them.

```cpp
int i = 0;
int a = i++;   // safe: one modification, one expression
int b = i;     // safe: different expression (sequenced by ;)

// Or:
int j = 0;
int x = j;
j++;           // safe: sequenced by separate statements
```

## Chapter 6: Null Pointer Dereference — The Optimization Nobody Expects

### The Basic Case

```cpp
int* p = get_pointer();
*p = 42;  // UB if p is null
```

If `p` is null, dereferencing it is UB. Everyone knows this. What they don't know is what the compiler does with it.

### The Optimization

The compiler sees `*p = 42`. This dereferences `p`. Dereferencing a null pointer is UB. The compiler assumes UB doesn't happen. Therefore: `p` is not null at this point. This is information the compiler can use.

```cpp
void process(int* p) {
    *p = 42;                    // dereference — p is not null here
    if (p == nullptr) {         // check — but p can't be null (we just dereferenced it)
        handle_null_case();     // dead code — eliminated
    }
}
```

The null check after the dereference is eliminated. This seems fine — if you dereference first, the check is redundant. But the danger is when the sequence is:

```cpp
void process(int* p) {
    // ... some code that might set p to null ...
    
    if (p != nullptr) {
        log("pointer is valid");
    }
    
    *p = 42;  // dereference
    
    // Compiler: p was dereferenced, so p != null here
    // Working backward: if p != null here and p wasn't changed between
    // the if and the dereference, then p != null at the if too
    // Therefore: the if condition is always true
    // log() always executes
    // The if is dead code — can remove the branch
}
```

The compiler can propagate the non-null information backward through the code and eliminate safety checks that appeared before the dereference — even though those checks came first in source order.

### The Real-World Version

```cpp
// From a real Linux kernel CVE (paraphrased)
void handle_request(struct request* req) {
    // Use req (dereference)
    process(req->data);
    
    // "Safety" check after use — the compiler may eliminate this
    if (req == NULL) {
        log_error("null request");
        return;  // dead code
    }
    
    // Privilege escalation code that should never run for null req
    elevate_privileges(req->user_id);  // runs even for null req
}
```

The "safety" check was added later as a defense-in-depth measure. The compiler eliminates it because the prior dereference proves non-null. Result: a security vulnerability.

### The Fix

Check before dereferencing. In that order. Always.

```cpp
void process(int* p) {
    if (p == nullptr) {      // check first
        handle_null_case();
        return;
    }
    *p = 42;                 // dereference after — safe
}
```

The compiler cannot eliminate a null check that comes before the dereference — it doesn't yet have the "p was dereferenced, so it's non-null" information at that point.

## Chapter 7: Object Lifetime Violations — Use After Free And More

### The Basic Cases

```cpp
// Use after free
int* p = new int(42);
delete p;
int x = *p;  // UB: object's lifetime ended at delete

// Stack use after return
int* bad_pointer() {
    int local = 42;
    return &local;  // local's lifetime ends when function returns
}
int* p = bad_pointer();
int x = *p;  // UB: local is gone

// Use before construction
struct Foo {
    int x;
    Foo() : x(42) {}
};
Foo* p = (Foo*)malloc(sizeof(Foo));  // allocated but not constructed
int y = p->x;  // UB: Foo hasn't been constructed yet
new(p) Foo();  // now it's constructed
int z = p->x;  // OK
```

### What The Compiler Does With Lifetime UB

**The use-after-free optimization:**

```cpp
int* p = new int(42);
// ... code that uses p ...
delete p;
// ... more code ...
// Compiler: p points to freed memory. Accessing freed memory is UB.
// Therefore: after the delete, any access through p is UB.
// Therefore: the compiler can assume no code accesses p after delete.
// Therefore: the compiler can assume p's value doesn't matter after delete.
// Optimization: reuse p's storage (a register) for something else.
```

If you then access `*p` — the register now holds a different value. You get a completely different integer, not the old value, not garbage — something meaningful to a completely unrelated computation.

**The dangling reference optimization:**

```cpp
// Returns a reference to a local — UB but common mistake
const int& get_value() {
    int x = compute();
    return x;  // x's lifetime ends here
}

void caller() {
    const int& val = get_value();
    // val is a dangling reference — UB to use it
    
    // But the compiler might:
    // 1. Inline get_value()
    // 2. See that x was computed as compute()
    // 3. See that val refers to x
    // 4. Optimize away the copy — use the return value register directly
    // 5. The "dangling reference" actually works — by accident
    
    use(val);  // appears to work in debug; breaks in release
}
```

This is the most insidious lifetime bug. It works in debug because the stack memory hasn't been overwritten yet. It fails in release because the optimizer restructured the code and the "dangling" location now holds something else.

### The std::optional Lifetime Trap

```cpp
std::optional<int> get_optional() {
    return std::nullopt;
}

void dangerous() {
    int& ref = *get_optional();  // UB: dereferencing empty optional
    // The compiler may:
    // - Return a reference to uninitialized storage
    // - Assume the optional is non-empty (because dereferencing empty is UB)
    // - Optimize based on that assumption
    use(ref);
}
```

Use `value()` instead of `*` when you want an exception on empty, or check `has_value()` before `*`.

## Chapter 8: Uninitialized Variables — The Invisible Corruption

### Why Uninitialized Variables Are UB (Not Just Garbage)

```cpp
int x;         // uninitialized
int y = x + 1; // UB
```

Most engineers think: "x contains whatever was in memory at that address. Probably garbage. But defined garbage."

The standard says: reading an uninitialized variable with indeterminate value is UB (for most types — specifically those that are not unsigned char).

The compiler uses this UB to assume: `x` has whatever value makes the rest of the code most optimizable. It may produce different values in different parts of the same expression.

**The impossible result:**

```cpp
int x;  // uninitialized
if (x > 0) {
    // Compiler: x > 0 here
    printf("%d\n", x);  // might print negative number
}
```

How can x be > 0 in the condition but negative in the printf? Because the compiler is allowed to use different "instances" of x's indeterminate value. In the condition, it uses a value that makes the branch taken. In the printf, it uses the actual register content, which might be anything.

This is not theoretical. It has been observed in real programs with `gcc -O2`.

### The Indeterminate Value Rule

For types that can hold trap representations (most types on real hardware), reading an uninitialized value is UB. For `unsigned char`, reading an uninitialized value produces an unspecified (but defined) value — not UB.

This means: memset to zero is safe as initialization for unsigned char arrays. It is not sufficient for proper initialization of other types (the value might be "defined" but the object is not properly initialized).

### Detection

```bash
# GCC/Clang: catches many uninitialized uses
-Wall -Wuninitialized

# Valgrind: runtime detection of all uninitialized reads
valgrind --track-origins=yes ./program

# AddressSanitizer + MemorySanitizer (MSan): catches more cases
clang -fsanitize=memory ./program
```

MemorySanitizer is the gold standard for uninitialized read detection. It instruments every memory operation and tracks which bytes have been initialized. More comprehensive than static analysis, more informative than valgrind.

## Chapter 9: The UB Sanitizers — Your Production Defense

The theoretical understanding of UB is only half the story. In practice you need tools to find it in existing code.

### AddressSanitizer (ASAN)

Detects:
- Use after free
- Stack/heap buffer overflows
- Use after return
- Use after scope
- Double free

```bash
clang++ -fsanitize=address -fno-omit-frame-pointer -g your_file.cpp
./a.out
```

Runtime overhead: ~2x slowdown, ~3x memory increase. Use in testing, not production.

### UndefinedBehaviorSanitizer (UBSAN)

Detects:
- Signed integer overflow
- Null pointer dereference
- Misaligned access
- Shift-count overflow
- Invalid enum values
- Out-of-bounds array access (in some cases)

```bash
clang++ -fsanitize=undefined -g your_file.cpp
./a.out
```

Runtime overhead: ~1.5x slowdown. Can be used in production on non-critical paths.

Sample UBSAN output:

```
file.cpp:15:13: runtime error: signed integer overflow: 
2147483647 + 1 cannot be represented in type 'int'
```

Exact location, exact operation, exact values. Turn on UBSAN in your CI pipeline and treat every UBSAN report as a critical bug.

### MemorySanitizer (MSAN)

Detects:
- Uninitialized memory reads

```bash
clang++ -fsanitize=memory -fPIE -pie -g your_file.cpp
./a.out
```

Overhead: ~3x slowdown. Requires all dependencies to be compiled with MSAN (otherwise false positives).

### ThreadSanitizer (TSAN)

Detects:
- Data races

```bash
clang++ -fsanitize=thread -g your_file.cpp
./a.out
```

Overhead: ~5-15x slowdown, ~5-10x memory. Use on multithreaded code specifically.

### The Production Strategy

```
Development:     -fsanitize=address,undefined (always on)
CI pipeline:     ASAN + UBSAN + TSAN (separate runs, different test suites)
Pre-release:     MSAN run on full test suite
Production:      -fsanitize=undefined (low overhead subset) on canary fleet
```

Adobe's SDK teams run ASAN and UBSAN on every commit. TSAN runs nightly on the concurrency-heavy components. MSAN runs weekly on the rendering pipeline.

## Chapter 10: The Complete Mental Model — How To Think About UB

### The Compiler's Reasoning Process

When the compiler encounters code, it builds a model of what's possible. UB is a permission to prune that model aggressively:

```
Code: if (x + 1 > x)

Compiler reasoning:
1. x is a signed int
2. x + 1 > x requires x + 1 to be computed
3. If x + 1 overflows: UB (signed overflow)
4. UB doesn't happen (assumption)
5. Therefore: x + 1 doesn't overflow
6. For all non-overflowing signed integers: x + 1 > x is true
7. Condition is always true
8. Else branch is unreachable
9. Delete else branch
```

The compiler is not being malicious. It is being logical. You made a promise (no UB). The compiler relied on that promise to build an optimization. You broke the promise. The optimization produced wrong results.

### The Seven Questions To Ask About Any Code

Before writing or reviewing concurrent/systems code:

1. **Does any signed integer computation risk overflow?**
   → Use unsigned, check before computing, or use overflow builtins

2. **Does any pointer access an object of a different type?**
   → Use memcpy or std::bit_cast for type punning

3. **Is there any shared non-atomic data accessed without synchronization?**
   → All shared data must be `std::atomic` or protected by a mutex

4. **Does any expression modify and also read the same variable?**
   → Separate into sequenced statements

5. **Does any dereference happen before a null check?**
   → Check before dereference, always

6. **Is any memory accessed after its lifetime has ended?**
   → Use ASAN to verify

7. **Are all variables initialized before first read?**
   → Use MSan to verify, use `-Wuninitialized` as static check

### The Line That Stops Interviews Cold

When asked about UB, say this:

> "UB is not a runtime concept — it's a compile-time permission. When the compiler encounters code that could only execute if UB had occurred, it doesn't crash or warn. It assumes UB doesn't exist and optimizes on that assumption. The dangerous cases are when that assumption propagates backward through the optimization graph and eliminates code that appeared before the UB — safety checks, null guards, range validation. I've seen real CVEs caused by exactly this: a compiler eliminating an overflow check or a null pointer check because a subsequent dereference proved non-null. The defense is sanitizers in CI and static analysis in review — not relying on UB "usually working."

That answer demonstrates you understand UB mechanistically, not just as a list of rules to memorize.

## The Unifying Insight

Every category of UB follows the same structure:

```
1. The hardware does something defined
   (x86 wraps on overflow, null deref causes SIGSEGV, etc.)

2. The standard says: this is UB
   (for performance, simplicity, or portability reasons)

3. The compiler assumes UB doesn't happen
   (uses this assumption to optimize aggressively)

4. When UB does happen:
   (the compiler's optimization produces impossible results)
   (not wrong results — impossible results, from hardware-level reasoning)
```

The gap between what the hardware does and what the standard requires is where UB lives. The compiler sits in that gap, building optimizations on the standard's guarantees. When you violate those guarantees, the optimizations produce behavior that no human reasoning about the hardware would predict.

That is why UB is uniquely dangerous. It doesn't produce consistently wrong results you can debug. It produces results that are correct from the compiler's perspective but impossible from the hardware's perspective — depending on optimization level, platform, and compiler version.

The only defense is to never invoke it. The sanitizers tell you when you do.
